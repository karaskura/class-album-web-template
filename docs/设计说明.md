# 班级相册 · 设计说明

这份文档记录"为什么这么做"，代码本身怎么写在 [`web/`](../web) 和 [README](../README.md) 里。

## 一、需求从哪来

原始需求只有一句话：

> 我想设计一个班级相册软件，仅限我们班学生使用（电脑和手机互通版）

加上两条后来明确的约束：

1. **不能访问外网** —— 确切地说，是不能依赖 GitHub / Vercel / Supabase 这类国外服务，同学的网络也要能正常访问
2. **最后选了方案 A** —— 国内云服务（可以在校外访问），而不是纯局域网方案

于是推导出的硬性要求：

| 要求 | 怎么落地 |
|---|---|
| 仅限本班 | 邀请码 + 学号 + 管理员审批；照片短时签名地址 |
| 电脑手机互通 | 响应式 Web + PWA，一套代码 |
| 不依赖国外服务 | 国内服务器 + 自建数据库 + 阿里云 OSS |
| 成本可控 | 普通云主机 + 对象存储按量付费，成本很低 |
| 低配云主机也扛得住 | 图片在浏览器压缩、直传对象存储，服务器只发凭证 |

## 二、几个关键决策

### 2.1 形态：响应式 Web + PWA

对比过小程序和原生 App，最后选 Web：

- 小程序：个人主体难上线，照片类内容还有审核风险
- 原生 App：iOS / Android 两套，开发分发成本太高
- **响应式 Web + PWA**：一套代码，免安装、免审核、更新即时；加到主屏幕后体验接近 App

代价是 iOS 上推送和后台能力弱、部分国产浏览器对 PWA 支持不完整。
但班级相册不需要推送，这个代价可以接受。

### 2.2 私密性：三道锁

这是整个项目最重要的一件事。做法：

1. **进不来**：关闭公开注册 → 邀请码（一码一用，可限定学号）→ 管理员审批后才激活
2. **看不到**：所有照片必须通过 `/api/media/...` 读取，这个接口先校验登录态；
   换成 OSS 后返回 302 跳到几分钟就过期的签名地址
3. **拿不走**：对象存储桶设为私有；上传地址由服务端签发（local 驱动下是 HMAC 令牌）

> 直链泄露是同类项目最常见的翻车点。所以**任何地方都不要把 OSS 的真实 URL 直接写进页面**，
> 一律走 `mediaUrl()`。

### 2.3 存储：写一个适配层，local 和 OSS 二选一

一开始就用 OSS 的话，你还没跑起来就得先掏钱开服务、配 CORS，很容易卡住。

所以 `lib/storage.ts` 定义了一个 `StorageDriver` 接口，两个实现：

- `local`：文件写到服务器磁盘，上传走 `/api/storage/put` 中转。
  **零成本、零配置，先跑起来看效果**
- `oss`：预签名 URL 直传（OSS V1 签名，用 `node:crypto` 手写 HMAC-SHA1，
  没引 `ali-oss` 依赖），图出网不经过服务器

切换只改一个环境变量 `STORAGE_DRIVER`，页面代码一行都不用动。

### 2.4 图片处理放在浏览器，不放服务器

原方案里提到"上传时生成缩略图"。常见做法是服务器装 `sharp`，但：

- `sharp` 是原生依赖，装包容易出问题
- 低配机器每次上传都跑图像处理，并发几个就卡住了

所以改成**浏览器端用 canvas 生成三档**（480 / 1280 / 2560px，WebP），再分别直传。
> **关于时间轴用什么时间**：最早设计成用 EXIF 里的拍摄时间排序，后来改成**按发布时间**。
> 原因：用拍摄时间会出现"今天传的旧照片跑到去年去"的情况，而且大量照片没有 EXIF，
> 反而不好预期。现在时间轴、年度回忆一律看 `created_at`（发布时间）；
> EXIF 的拍摄时间只在照片详情页作为参考信息显示，不参与排序。

顺带解决了两个问题：

- **EXIF 隐私**：canvas 重新编码会把 EXIF 整块丢掉，拍摄地点不会留在图里
  （但我们会在丢掉之前把 `DateTimeOriginal` 读出来存进数据库，用于时间轴排序）
- **带宽**：手机拍的 8MB 原图，传到服务器前已经变成 1MB 左右

`lib/exif-client.ts` 里手写了一个精简的 EXIF 解析器（只找 JPEG APP1 里的拍摄时间），
没用 `exif-js` 之类的库。

### 2.5 认证：没用 NextAuth，自己写了

原方案说"Supabase Auth 换成 NextAuth + 自建用户表"。实际做的时候没用 NextAuth，原因是：

- 我们要的逻辑很特别：邀请码 + 待审批状态 + 封禁后立刻踢下线
- 用 NextAuth 反而要在它的回调里绕来绕去，代码更绕
- 自己写只需要 3 个文件：`lib/auth.ts`（scrypt 哈希）、`lib/session.ts`（会话 cookie）、
  几个 `/api/auth/*` 路由

会话存数据库而不是签名 JWT，好处是**管理员停用某人时可以立刻删掉他的会话**
（JWT 在过期前一直有效，踢不掉）。

### 2.6 前端不用 Tailwind，手写 CSS

原方案提到了 Tailwind。这里改成了手写 CSS + CSS 变量，原因：

- 依赖越少越好装，`node_modules` 越小，构建越快
- 浅色/深色两套主题用 CSS 变量表达最直接
- 那份 UI 预览稿（`preview/index.html`）也能复用同一套色值，视觉完全一致

样式全在 `web/app/globals.css`，顶部是设计 token，改主题只改那一段。

## 三、数据表

`web/db/schema.sql`，7 张表：

| 表 | 干什么 | 关键字段 |
|---|---|---|
| `users` | 成员 | `student_no`、`password_hash`、`role`(member/admin)、`status`(pending/active/disabled) |
| `invites` | 邀请码 | `code`、`bound_student_no`、`used_by`、`expires_at` |
| `sessions` | 登录会话 | `id`(随机 32 字节)、`user_id`、`expires_at` |
| `albums` | 相册分组 | `name`、`event_date`、`cover_photo_id` |
| `photos` | 照片 | `storage_key`/`thumb_key`/`micro_key` 三个 key、`taken_at`、`status`(软删除) |
| `comments` | 评论 | `photo_id`、`user_id`、`content` |
| `likes` | 点赞 | 联合主键 `(photo_id, user_id)`，天然防重复点赞 |

设计上的几个考虑：

- **一张照片存三份对象**，数据库里存三个 key。列表页只加载 `micro`，点开才加载 `thumb`，
  下载才用原图 —— 这是相册类应用省流量的核心
  - **2026-10-05 变更**：`orig` 不再对普通成员开放（维护者要求取消下载、防图片被盗用）。
    三档存储不变，但 `/api/media/...` 里 `orig.*` 只放行管理员；页面只发 `thumb`，
    上传（直传签名 URL）和归档（服务端读盘）都不受影响
- **照片不物理删除**，`status` 置为 `deleted`。删错了还能捞回来，也不会把对象存储搞乱
- **外键都带 `on delete set null`**：用户被删掉后照片还在，只是显示"已注销的同学"，
  不会连带把整个班相册清空
- 索引建在排序和过滤真正会用到的列上：`taken_at desc`、`album_id`、`uploader_id`、`status`

## 四、两个关键流程

### 4.1 上传（三个阶段）

```
浏览器                     我们的服务器                    对象存储(OSS/本地)
  │                            │                                │
  │─ ① 选中照片，本地压缩 ──────┤                                │
  │   canvas → micro/thumb/orig│                                │
  │                            │                                │
  │─ ② POST /api/upload/init ─▶│  分配 3 个 key + 签发上传地址    │
  │◀──── { targets: [...] } ───┤                                │
  │                            │                                │
  │─ ③ 直接 PUT 三次 ──────────────────────────────────────────▶ │
  │   (带进度条，图片不经过服务器)                                │
  │                            │                                │
  │─ ④ POST /api/upload/commit▶│  校验路径合法性 → 写入 photos 表 │
  │◀──────── { count } ────────┤                                │
```

拆分的原因：**图片流绝不经过我们的服务器**。否则低配机器传几张原图就爆内存和带宽了。

### 4.2 读图

```
浏览器 ── GET /api/media/photos/2026/09/xxxx/thumb.webp ──▶ 服务器
                                                          │
                                        ① 校验登录态（没登录 → 401）
                                        ② local 驱动：直接读磁盘返回
                                           oss 驱动：302 → OSS 短时签名地址
```

**为什么不直接把 OSS 签名地址渲染进页面？** 也可以（`mediaUrl()` 在 OSS 驱动下确实返回签名 URL），
但保留 `/api/media` 这个入口有个好处：将来要加"水印""访问日志""限速"都只需要改一处。

## 五、和原方案的差异

| 原方案 | 实际实现 | 为什么改 |
|---|---|---|
| Supabase（Auth + Storage + Postgres） | 自建 PostgreSQL + 自写认证 + OSS | 不能用国外服务 |
| Vercel / Cloudflare Pages | 国内轻量服务器 + Docker + Caddy | 同上 |
| NextAuth + 自建用户表 | 自己写会话（session 存库） | 需要"封禁即踢下线"，逻辑更直接 |
| 服务器端 sharp 生成缩略图 | 浏览器端 canvas 生成三档 | 低配机器扛不住，且避免原生依赖 |
| Tailwind CSS | 手写 CSS + CSS 变量 | 减少依赖，和预览稿共用色值 |
| 人脸聚类、地图足迹、年度回忆 | 未实现（列为后续） | 先把 MVP 闭环跑通 |
| 学号名单批量导入 | 已实现（后台粘贴名单 → 生成绑学号的专属邀请码） | 补上了，见 `api/admin/roster` |

## 六、已知的取舍与风险

1. **PGlite 只适合本机预览**。`npm run dev:db` 用的 WASM 版 Postgres 是单连接数据库，
   靠多路复用模拟并发，压力大时可能不稳。正式部署一定用 docker-compose 里那个真 Postgres。
2. **OSS 必须配 CORS**，否则浏览器直传会失败，而且报错信息不直观。README 第 6.2 节专门写了。
3. **照片走 `/api/media` 时每张图都要过一次鉴权**，比直连 CDN 慢一点。
   班规模（几千到几万张）无所谓，真到了十万级再考虑把签名 URL 直接渲染进页面。
4. **没有自助改密**，也没有忘记密码流程。班级场景里管理员手动处理是可以接受的。
5. **Service Worker 刻意不缓存照片**。这是私密相册，共用电脑时不能把别人的照片留在缓存里。
   代价是断网时只能看到离线提示页。

## 七、如果继续做，建议的顺序

1. 自助改密码（最容易加，同学一定会问）
2. 管理后台加"删除照片"按钮（后端已经写好了）
3. 照片按活动 / 人物筛选
4. 人脸聚类（技术复杂度陡增，放最后）
